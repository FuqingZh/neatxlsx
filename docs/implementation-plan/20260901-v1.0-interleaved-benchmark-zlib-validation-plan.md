# Interleaved Benchmark and Native zlib Validation Plan

Version: v1.0
Date: 2026-09-01
Status: active

## Objective

Replace the shared-host-sensitive serial comparison procedure with a fixed
harness that alternates two isolated neatxlsx builds in fresh processes. Use
that harness to determine whether the `rust_xlsxwriter 0.90.2` `zlib` feature
actually changes the active compression backend and, only if it does, whether
the performance benefit justifies its build and wheel portability cost.

This plan has two independent acceptance boundaries:

1. the interleaved benchmark harness must be correct and reviewable before it
   is used as performance evidence; and
2. enabling native zlib must pass backend-identity, performance, output-parity,
   and distribution gates before it can become a production dependency.

The existing single-pass benchmark remains a frozen historical result. The
follow-up investigation is diagnostic evidence, not retroactive acceptance.

## Current evidence and constraints

- The branch is based on single-pass implementation commit `4f08fd6` and
  performance-investigation commit `072c424`.
- The original huge benchmark ran baseline samples before candidate samples.
  Its `none` regression was not reproduced by later ABBA-style measurements.
- The current benchmark imports one checkout in-process, runs one revision at
  a time, and records only end-to-end wall time.
- `rust_xlsxwriter 0.90.2` enables `zip 4.6.1`'s `deflate` feature. The resolved
  graph already selects `flate2 1.1.9` with `zlib-rs 0.6.6`.
- `flate2 1.1.9` gives `zlib-rs` priority over stock C zlib when Cargo's
  additive features select both. Enabling `rust_xlsxwriter/zlib` may therefore
  add `libz-sys` without changing the active compressor.
- The release workflow still asserts bridge ABI/contract v5 in two smoke
  commands. It cannot serve as the zlib wheel oracle until those assertions
  are synchronized with ABI/contract v6.
- Performance is host-specific. Cross-platform wheel validation proves build
  and import viability, not equivalent speed on every platform.

## Non-goals

- Do not change XLSX values, styles, widths, pagination, ZIP64 policy, public
  Python signatures, or bridge semantics.
- Do not weaken the original single-pass performance gate or rewrite its
  recorded result.
- Do not retain an experimental C dependency when it is not the active
  compressor or does not meet the adoption threshold.
- Do not use compressed archive bytes or file size as the sole semantic oracle.
- Do not publish packages, create tags, or push release artifacts.

## Slice 1: fixed single-run worker

Extend `scripts/benchmark_xlsx_writer.py` without removing its existing
single-checkout CLI. Add an internal single-run mode used by the comparison
driver. It accepts:

- an explicit package root and expected native path boundary;
- one named scenario and a pre-generated fixture path;
- one output path and logical run identifier;
- `max_rows`, chunk size, CPU affinity, and Polars thread policy; and
- a JSON result path.

The worker must set affinity and thread policy before importing Polars or
neatxlsx. It must verify that `neatxlsx.__file__` and `_native.__file__` belong
to the requested checkout, that the backend is a release build, and that the
bridge metadata is present. It records package/native paths, bridge metadata,
native SHA-256, Python/Polars versions, and scenario identity.

Use explicit workbook lifecycle calls to time:

1. input-plan construction;
2. `write_sheet()` wall and process CPU;
3. `close()` wall and process CPU; and
4. total wall and process CPU.

Capture the process RSS high-water mark after `write_sheet()` and after close.
Label it as process-start-to-stage high-water memory. Validate the workbook
only after all timed stages, then record output size and a manifest of SHA-256
hashes for every uncompressed ZIP member. Clean up through the public abort
path on worker failure.

## Slice 2: interleaved comparison driver

Add `scripts/compare_xlsx_writer.py`. It receives baseline and candidate Python
executables and package roots, but always invokes the worker code from the
current harness checkout. This keeps benchmark logic identical while allowing
each child interpreter to load its own package and native extension.

For each scenario:

1. create deterministic fixtures outside the timed region;
2. run one warmup for each revision in a balanced order;
3. generate four ABBA/BAAB blocks from a recorded seed, producing eight
   measured samples per revision;
4. launch every sample in a fresh process;
5. retain the exact planned and completed order, including failures; and
6. write raw JSONL before computing a Markdown/JSON summary.

The driver must reject:

- identical baseline and candidate native hashes when distinct builds were
  required;
- package/native paths outside their declared roots;
- non-release backends;
- mismatched scenario, fixture, chunk, autofit, or sampling policies;
- missing or duplicate run identifiers; and
- output directories that overlap either compared package root.

An interrupted or failed run remains inspectable but is not eligible for an
acceptance verdict. A rerun uses a new result directory rather than silently
overwriting partial evidence.

## Slice 3: metrics and verdict

For each scenario, pair temporally adjacent baseline/candidate observations
within the balanced blocks. Report candidate/baseline ratios for:

- total wall and process CPU;
- write wall and process CPU;
- close wall and process CPU;
- write-stage and close-stage RSS; and
- output size.

The primary acceptance metric is paired total wall time. Write/close CPU and
RSS explain the mechanism but cannot replace the end-to-end requirement.

Use at least eight measured samples per revision. Compute the paired median
ratio and a deterministic 95% bootstrap confidence interval using the recorded
analysis seed. Predeclare these gates:

- LazyFrame `body/all`: confidence-interval upper bound below `1.00` and median
  total-wall improvement of at least 3%;
- `none/header`: confidence-interval upper bound below `1.03`, excluding a
  regression of 3% or more; and
- every compared workbook: identical uncompressed ZIP-member names and bytes,
  after normalizing only the generated `docProps/core.xml` `created/modified`
  UTC values. Retain raw hashes before normalization. No other member or field
  is normalized unless a later reviewed amendment names it explicitly.

If the interval is too wide, record `inconclusive`. Do not increase samples
until a preferred answer appears. A new run with a predeclared larger sample
count or a quieter host is separate evidence.

The scenario matrix contains:

- existing default and huge DataFrame/Parquet LazyFrame cases;
- `none`, `header`, `body`, and `all`;
- default `max_rows=20_000` and explicit `max_rows=None`; and
- a fixed computed LazyFrame whose expression graph is part of the manifest.

## Slice 4: tests and protocol migration

Add focused tests for:

1. deterministic ABBA/BAAB generation and balance;
2. package/native containment checks;
3. fresh-process execution and failure retention;
4. stage timing and post-timing validation boundaries;
5. exact fixture/policy matching;
6. ZIP-member manifest equality and mismatch reporting;
7. bootstrap determinism and verdict thresholds;
8. partial-run non-acceptance and no overwrite; and
9. JSONL/summary consistency.

Update the benchmark protocol to make interleaved comparison the current
acceptance procedure. Keep the original serial rule only in its dated result
record. Synchronize the release workflow's wheel and installed-sdist smoke
assertions with bridge ABI 6 before using that workflow for zlib validation.

Run the smallest script tests first, then `pdm run check`, `git diff --check`,
and `git status --short`.

## Slice 5: isolated zlib backend canary

Start from one exact single-pass source commit and prepare two isolated release
builds with separate virtual environments, Cargo target directories, and output
directories:

- control: current `constant_memory` feature set;
- experiment: current features plus `rust_xlsxwriter/zlib`.

Do not enable zlib by default during this canary. Record the source SHA,
`Cargo.lock`, full feature trees, native hashes, binary sizes, and platform
linkage for both builds.

### Backend-identity stop gate

Prove the active compressor using the resolved feature tree, linked libraries,
and sampled native symbols from an XLSX workload.

If the experiment still spends compression time in `zlib_rs::*`, stop and
record the feature as an ineffective optimization for the current dependency
graph. Remove the experimental feature/dependency change. Do not run a formal
performance acceptance campaign merely to measure a known identical backend.

Only continue when the experiment demonstrably executes the intended native C
zlib path.

## Slice 6: zlib performance and adoption gates

When the backend-identity gate passes, use the accepted interleaved harness on
ZIP-heavy huge scenarios: tall `none`, wide `header/body/all`, and wide `all`
with `max_rows=None`.

Adopt native zlib only when all of these hold:

- paired total-wall median improves by at least 5%, with the 95% confidence
  interval entirely below `1.00`;
- close time/CPU improves consistently with the total result;
- write time has no regression of 3% or more;
- all uncompressed ZIP members are byte-identical;
- workbook reference, split-boundary, ZIP64, and reader checks pass; and
- the dependency/build change passes the release distribution matrix.

The 5% practical threshold is intentionally stricter than the single-pass
harness threshold because a C dependency expands build, security, and wheel
portability obligations.

## Slice 7: distribution validation

Build and install the five supported wheels:

- manylinux x86_64;
- manylinux aarch64;
- macOS x86_64;
- macOS arm64; and
- Windows AMD64.

Also build and install the sdist in a clean environment. Inspect Linux wheel
policy/dependencies, macOS linked libraries, and Windows DLL requirements.
Verify ABI3, bridge ABI/contract v6, release profile, package contents, and the
public `Workbook.write_sheet()` signature.

Local Linux success is insufficient evidence for the other platforms. If the
authorized workflow cannot be run, record those lanes as unchecked and do not
adopt the feature.

## Planned commits

2. `test(bench): add interleaved XLSX comparison harness`
3. `ci: align release smoke with bridge v6`
4. `docs: record native zlib backend canary`
5. `perf: enable native zlib compression` only if every adoption gate passes

The canary documentation commit is retained whether the experiment succeeds or
stops. An ineffective or nonportable feature change is not retained.

## Completion conditions

The plan is complete when:

- the interleaved harness and its protocol are committed and pass the complete
  repository gate;
- a clean off/on build proves the actual compressor identity;
- the canary result, commands, identities, and stop/adoption decision are
  retained; and
- native zlib is either adopted with full evidence or explicitly rejected with
  no production dependency left behind.
