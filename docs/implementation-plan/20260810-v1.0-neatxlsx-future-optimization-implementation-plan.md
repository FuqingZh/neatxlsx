# neatxlsx Future Optimization Implementation Plan

Version: v1.0
Date: 2026-08-10
Status: accepted direction; M0 and M1 implemented locally; M2+ not started

## Authority and scope

This document records the accepted product priorities, delivery sequence, and
acceptance gates for future neatxlsx optimization. It does not describe current
behavior and does not by itself add a public API commitment.

Current behavior remains governed by the
[architecture](../architecture/20260728-v1.0-neatxlsx-architecture.md),
[public API contract](../architecture/20260728-v1.0-neatxlsx-public-api-contract.md),
and [test plan](../testing/20260728-v1.0-neatxlsx-test-plan.md). A candidate
interface in this plan becomes a contract only after its implementation,
contract tests, type declarations, and current documentation land together.

The scope remains the stable path from a Polars table to a high-quality XLSX
report table. The plan does not turn neatxlsx into a generic report engine or
an editor for arbitrary existing workbooks.

The proposed detailed semantics and ordered delivery work for M0/M1 are in the
[M0/M1 report-trust design proposal](../architecture/20260811-v1.0-neatxlsx-m0-m1-report-trust-design-proposal.md)
and its
[implementation plan](20260811-v1.0-neatxlsx-m0-m1-report-trust-implementation-plan.md).
They do not describe current runtime behavior until the corresponding slices
are implemented and the current contracts are updated.

## Goal

Make neatxlsx the easiest way to produce a trustworthy and presentable XLSX
report from Polars:

- values and displayed meanings are correct by default;
- ordinary reports look complete without extensive configuration;
- headers, column roles, formats, and multiple sheets remain easy to compose;
- advanced Excel editing is available through one managed interoperability
  boundary; and
- large and lazy inputs retain streaming, bounded-memory behavior without
  making performance engineering the product's main interface.

## Accepted product direction

The priorities are ordered as follows:

1. **XLSX report-table experience** is the primary product direction. Within
   it, correctness precedes default presentation, and default presentation
   precedes additional expressiveness.
2. **Managed openpyxl interoperability** is the second priority. It is an
   escape hatch for the workbook produced by neatxlsx, not a second workbook
   model and not an existing-file editor.
3. **Performance and scale** are supporting constraints. LazyFrame support,
   streaming batches, automatic splitting, memory use, and temporary storage
   are improved from measurements while reusing Polars, Arrow, and
   rust_xlsxwriter.
4. **Additional ecosystem adapters** are demand-driven. They are not added
   merely to mirror another library's surface.

These priorities are compatible: the report path owns the common experience,
the openpyxl boundary owns uncommon editing, and the performance track protects
the report path without expanding its public vocabulary.

## Current baseline

The following capabilities already exist and must not be planned again as new
features:

- Polars `DataFrame` and `LazyFrame` input through Arrow C streams without a
  PyArrow runtime dependency;
- repeated and chained `write_sheet()` calls, loops that add sheets, context
  management, and explicit `close()`;
- multi-row custom headers, horizontal header merges, and frozen rows or
  columns;
- header, text, integer, decimal, and scientific-notation roles;
- automatic splitting at Excel row and column limits, worksheet-name
  normalization, and `report()` mappings from logical writes to physical
  worksheets;
- literal writes for formula-looking strings;
- ZIP64 by default;
- same-directory temporary output, retained POSIX permission bits, complete-file
  replacement, and retryable final replacement failure; and
- constant-memory Rust worksheets inside a wider batch-bounded pipeline.

The current architecture also establishes two important scale qualifications:

- `Autofit(mode="none")` and `Autofit(mode="header")` use one LazyFrame data
  source; body-aware modes currently require a second source; and
- total memory is not a strict size-independent constant because batch size,
  column count, headers, and format planning still contribute.

## Known gaps that shape the sequence

The first work is semantic rather than cosmetic:

- temporal, decimal, categorical, and other non-primitive Arrow values need an
  explicit Polars-to-Excel mapping instead of a fallback representation;
- integers and decimals that exceed Excel's exact numeric range must never be
  silently rounded;
- unsupported dtype policy should be decided from the schema before native
  generation starts;
- format values need early validation; and
- user format overrides need deterministic precedence, including border
  fields currently cleared by the base body-format patch.

The public signatures are already broad. Future report features therefore need
one cohesive extension point rather than parallel arguments or simultaneous
`Theme`, `TableStyle`, and `ColumnSpec` hierarchies.

## Cross-cutting invariants

Every milestone preserves the following unless a separately reviewed contract
explicitly replaces one:

- input strings are written literally and never inferred as formulas;
- logical tables split safely at Excel limits, with stable `report()` offsets;
- default output continues to use ZIP64 container features and requires a
  ZIP64-capable reader;
- generation failure does not replace an existing target;
- final replacement remains retryable after a completed temporary file exists;
- filesystem atomicity and durability are described with the qualifications in
  the current architecture rather than as unconditional guarantees;
- the ordinary writer path stays streaming and batch-bounded;
- Python owns caller policy, validation, Polars integration, and lifecycle;
- Rust owns XLSX mechanics, value conversion, worksheet planning, OOXML, and
  ZIP64; and
- the PyO3 crate remains a bridge without product policy.

## Capability admission rule

A feature belongs in the neatxlsx core report path only when all four
conditions hold:

1. it is a frequent report-table need;
2. it can work by default or through a small declarative configuration;
3. it composes with ordered streaming, automatic splitting, and transactional
   delivery; and
4. its output semantics are structurally testable.

Features that fail this test belong in an openpyxl recipe or the managed
interoperability phase. Repeated real-world demand is required before adding a
new adapter or public abstraction.

## Delivery map

| Milestone | Outcome | Public-contract effect |
| --- | --- | --- |
| M0 | Reproducible report reference set | None |
| M1 | Trustworthy values and format semantics | Dtype and formatting contract updates |
| M2 | Strong default report experience | Small, reviewed report-configuration additions |
| M3 | Managed openpyxl escape hatch | One planned lifecycle method and optional dependency |
| M4 | Measured scale and performance improvements | None by default |

Milestones are ordered by dependency, not by a promised calendar. Each should
be delivered in independently reviewable slices rather than one cross-cutting
rewrite.

## M0: report reference set

### Purpose

Make “correct, convenient, and presentable” reviewable before changing output
defaults or adding public configuration.

### Reference scenarios

Maintain source-controlled generators for at least these scenarios:

1. an ordinary scientific results table with identifiers, counts, decimals,
   missing values, and significance-like values;
2. a mixed-dtype table covering the temporal, decimal, boolean, categorical,
   and precision decisions needed by M1;
3. a multi-level header table with horizontal merges;
4. a pipeline-style workbook written through repeated or looped
   `write_sheet()` calls; and
5. tall, wide, and automatically split tables.

Generated workbooks are test or release artifacts rather than binary hash
contracts.

### Verification

Use the existing three independent XLSX oracles:

- openpyxl for reader-observed cell values, cell kinds, styles, freezes, and
  literal-string behavior;
- ZIP and OOXML assertions for container versions, worksheet parts, merges,
  and relationships; and
- compact JSON manifests for canonical logical-to-physical report structure.

Add a small visual rubric covering hierarchy, alignment, density, number
display, truncation, and consistency across split sheets. Excel and LibreOffice
inspection is representative release evidence, not a screenshot or binary-hash
pull-request gate.

### Acceptance

- all five scenarios can be regenerated from source;
- current behavior and known gaps are recorded without treating proposed
  output as current behavior;
- structured oracles cover the current safety invariants; and
- no public API is added in this milestone.

### Durable evidence

Keep scenario sources and manifests in the repository. Record future measured
performance results under `docs/benchmarks/` only after a reproducible run.

## M1: trustworthy values and format semantics

### Predecessor

M0 provides the scenarios and current-behavior baseline.

### Dtype policy

Define and test a matrix with these columns before changing the writer:

```text
Polars dtype -> Excel cell kind -> stored value -> displayed format
             -> precision, unit, and timezone policy
```

The initial matrix must decide at least:

- `Date`, `Datetime`, `Time`, and `Duration` storage and display;
- timezone-aware datetime rejection, normalization, or conversion, with no
  silent timezone removal;
- `Decimal` behavior inside and beyond Excel's exact numeric range;
- integer behavior beyond Excel's roughly 15 significant decimal digits;
- native or textual boolean behavior;
- `Categorical` and `Enum` label behavior; and
- deterministic rejection or explicit serialization policy for
  `List`, `Array`, `Struct`, `Binary`, `Object`, and other nested values.

The default must favor semantic safety: high-precision values are written as an
exact representation or rejected before writing, never silently rounded.

Python should reject unsupported schema types before native generation starts
so ordinary input errors remain `TypeError` or `ValueError` and do not poison a
workbook as a generation-time `WriteError`. Rust remains responsible for the
accepted value conversions.

### Format policy

- validate alignment, border, number-format, and other constrained values at
  the Python policy boundary;
- make user overrides effective for every supported field;
- establish and test this precedence:

  ```text
  default report style
  < inferred dtype role
  < Workbook role override
  < sheet or column rule
  < conditional overlay
  ```

- keep `Format` as a local cell-format patch rather than a theme or worksheet
  object.

### Verification

- matrix tests cover DataFrame and LazyFrame input;
- minimum and latest supported Polars lanes observe the same values;
- openpyxl and OOXML agree on stored kinds and formats;
- large integers and decimals never lose precision silently;
- formula-looking strings remain literal;
- unsupported schemas fail before writing the affected logical sheet and leave
  the workbook usable; and
- `pdm run check` passes after the public contract, type declarations, and
  documentation are updated.

### Acceptance

No reference scenario writes a dtype description in place of a data value.
Every supported dtype has an explicit stored-value and display contract, and
every unsupported dtype has a deterministic preflight error.

### Slice-local non-goals

- visual theme selection;
- title or note composition;
- charts, formulas, or arbitrary cell editing; and
- performance claims beyond detecting material regressions.

## M2: default report experience

### Predecessor

M1 stabilizes the values to which visual and column semantics apply.

### M2.1: opinionated default report

Make `write_sheet(data, "Results")` produce a restrained, complete report table
without manual integer and decimal column lists.

Candidate default decisions include typography, header contrast, subtle body
separation, alignment, type-driven number formats, conservative widths, frozen
headers, gridline visibility, and filtering. Exact colors, fonts, borders, and
view settings are selected against the M0 scenarios rather than committed by
this plan.

Changing defaults is a user-visible output change. The selected profile needs
before-and-after fixtures, release notes, and compatibility coverage.

### M2.2: one aggregated column-rule boundary

Prefer one declarative column-rule entry point over additional parallel
`*_columns` and `*_format` parameters. It should be able to select by column
name, index, ordered sequence, or Polars selector and describe a bounded set of
static report properties such as:

- semantic or explicit number format;
- width and alignment;
- display label; and
- hidden state.

The final parameter and public type names are an API-design checkpoint, not a
current contract. Before implementation, compare the smallest viable mapping
or value-object designs against signature growth, selector overlap, rule
precedence, error messages, typing, and split-sheet propagation.

Do not introduce separate theme, table-style, and column-specification object
families in the same slice. A public `theme` concept is justified only after at
least two stable, reusable visual profiles exist; the first strong default does
not require a theme API.

### M2.3: preserve the pipeline model

The intended multi-sheet lifecycle remains:

```python
with Workbook("report.xlsx") as workbook:
    for sheet_name, data in reports:
        workbook.write_sheet(data, sheet_name)
```

Document chaining, loops, explicit `close()`, failure behavior, and report
inspection with complete examples. Do not add a builder hierarchy or
`write_sheets()` convenience until evidence shows that the current model has a
real usability gap.

### M2.4: bounded report composition candidates

After the default and column boundary are stable, evaluate these in order:

1. autofilter, row banding, gridline visibility, and other common sheet-view
   choices;
2. title, subtitle, source notes, and simpler column labels or grouped headers;
3. stream-compatible threshold rules, color scales, data bars, and icon sets;
4. a narrow print layout for orientation, fit-to-width, repeated header rows,
   and margins; and
5. sparklines only after concrete report demand.

Each candidate still has to pass the capability admission rule. Excel Table
objects are not the default mechanism because they conflict with common
constant-memory implementations and complicate multi-row headers and automatic
splitting. Full chart, image, validation, comment, and shape APIs remain in the
openpyxl phase.

### Verification

- zero-configuration reference reports meet the M0 visual rubric;
- style and column rules propagate to every automatically split worksheet;
- overlapping selectors have deterministic resolution and diagnostics;
- multi-row headers and report offsets remain correct;
- `none` and `header` autofit retain a single LazyFrame data source;
- memory remains batch-bounded for the ordinary path; and
- public additions update signatures, stubs, exports, contract tests, examples,
  the API contract, and release notes together.

### Acceptance

An ordinary report is presentable with no style configuration, and common
column-specific formatting requires one coherent declarative boundary rather
than manual workbook editing.

## M3: managed openpyxl interoperability

### Predecessor

M1 is complete and the M2 report features selected for the first interoperability
release have stable round-trip expectations. M3 does not need to wait for every
later report-composition candidate.

### Planned interface, not current API

The accepted target is a no-argument `edit_with_openpyxl()` method:

- openpyxl remains optional, with a supported range of
  `openpyxl>=3.1.5,<4`;
- the default package import does not import or require openpyxl;
- the first call finalizes the neatxlsx generation phase, materializes the
  workbook, and enters a terminal editing phase;
- repeated calls return the same real `openpyxl.Workbook`;
- `write_sheet()` after the transition raises `StateError`;
- normal outer context exit or explicit neatxlsx `close()` saves and commits;
- direct `book.save()` or `book.close()` is outside neatxlsx lifecycle
  guarantees;
- there is no size threshold or `allow_materialize` flag, but the eager and
  non-bounded-memory nature of this phase is documented; and
- `report()` continues to describe only the neatxlsx generation phase.

The method edits the workbook generated in the current neatxlsx lifecycle. It
does not open an arbitrary existing workbook. `to_openpyxl()`, a generic
`WorkbookArtifact`, and a second wrapper workbook model are not planned.

### Error and transaction behavior

- a missing optional dependency raises `ImportError` with an installation
  hint;
- invalid lifecycle transitions or known incompatible features raise
  `StateError`;
- neatxlsx finalization, openpyxl load, and openpyxl save failures map to
  `WriteError` and abort the generation;
- final target replacement failure remains a retryable `CommitError`; and
- openpyxl save failure is not treated as a retryable final replacement.

User changes made through openpyxl are not audited for formula-literal safety,
report semantics, or other neatxlsx generation guarantees. This boundary is
explicit in the API contract and examples.

### ZIP64 and round-trip gate

The default `use_zip64=True` contract must still hold after the openpyxl phase;
`use_zip64=False` must remain an explicit legacy-reader opt-out. Tests inspect
the final ZIP and OOXML rather than prescribing a repackaging implementation.

Known incompatible core features are rejected before entering the editing
phase. Supported core features have an explicit round-trip matrix covering
values, styles, merges, freezes, splits, literal strings, permissions, reports,
and transaction outcomes.

### Acceptance

- context-managed and explicit-close lifecycles both commit successfully;
- dependency-minimum and dependency-latest lanes pass;
- failure and retry state matrices are contract tested;
- ZIP64/default and opt-out files satisfy their final container contracts; and
- the architecture, public API contract, package extra, stubs, and examples are
  updated in the same change that exposes the method.

## M4: measured scale and performance improvements

### Predecessor

M1 value semantics are stable. Benchmarks compare equivalent valid output, not
only execution time.

### Benchmark matrix

Measure reproducibly across:

- tall and narrow tables;
- wide tables;
- multiple sheets;
- DataFrame and LazyFrame sources;
- automatic row and column splitting;
- representative string cardinality and format density; and
- header-only versus body-aware autofit.

Record environment, input construction, wall time, peak resident memory,
temporary-disk high-water mark, final file size, and output validity. Establish
a measured baseline before selecting regression budgets or publishing
performance claims.

### Candidate optimizations

Prioritize only demonstrated bottlenecks, such as:

- Arrow batch sizing and conversion;
- format deduplication and cache locality;
- column-width sampling or one-pass alternatives where semantics permit;
- compression and temporary-file behavior; and
- physical split planning for extreme shapes.

Reuse Polars, Arrow, and rust_xlsxwriter rather than creating a DataFrame
engine, another XLSX writer, or a second format model.

### Verification and acceptance

- every benchmark validates values and report structure;
- optimized output remains semantically equivalent for the documented case;
- literal safety, ZIP64, split mappings, and transaction behavior do not
  regress;
- ordinary-path memory remains batch-bounded; and
- claims cite a committed benchmark record with the exact environment and
  inputs.

## Ecosystem follow-up

Pandas or Arrow users can initially convert to Polars at the input boundary.
Documentation recipes are preferred over thin adapters. Add an adapter only
when repeated usage shows that it removes real lifecycle, dtype, or
compatibility complexity rather than renaming an existing conversion.

No workbook-to-Polars or generic artifact conversion is planned. Polars owns
table semantics; openpyxl owns the advanced mutable workbook escape hatch.

## Deferred and out of scope

- a general cell or worksheet object model;
- reading and modifying arbitrary existing workbooks;
- complete formula, chart, image, validation, comment, or shape DSLs;
- a pandas Styler or CSS compatibility layer;
- a generic report-layout engine;
- remote object-store delivery;
- a self-developed DataFrame, query, or XLSX engine;
- `write_sheets()` without evidence that loops are insufficient;
- `to_openpyxl()` or a generic `WorkbookArtifact`; and
- Excel Table objects until streaming, multi-row-header, and split behavior is
  proven compatible.

## Compatibility and documentation gates

For every public change:

- treat `python/neatxlsx/__init__.py`, Python signatures, type declarations,
  exceptions, reports, tests, and documentation as one compatibility boundary;
- state whether existing output changes and whether a migration note is
  required;
- update the current API contract only when the feature is implemented;
- update the architecture when ownership, lifecycle, or the product boundary
  changes;
- update the test plan when a durable oracle or CI lane changes; and
- preserve Python 3.11+, abi3-py311, and minimum/latest Polars validation unless
  a separately reviewed support decision replaces them.

## Risks and controls

| Risk | Control |
| --- | --- |
| API growth recreates a full Excel engine | Enforce the admission rule and add one cohesive boundary at a time |
| Visual defaults churn between releases | Select against fixed scenarios and document user-visible output changes |
| Excel silently rounds precise values | Decide dtype mappings before conversion and reject or preserve exact values |
| Styling features break streaming or splitting | Prototype on physical split sheets and retain batch-bounded acceptance tests |
| openpyxl weakens safety or ZIP64 guarantees | Limit the audited boundary, test final artifacts, and document unmanaged edits |
| Performance work changes output semantics | Validate outputs in every benchmark and optimize only measured bottlenecks |
| Visual tests become brittle | Keep structural oracles primary and visual inspection as representative evidence |

## Rollback and cleanup

- M0 adds no runtime behavior and can be revised independently.
- M1 and M2 slices keep behavior and public-surface changes independently
  reviewable; a rejected candidate does not require reverting the reference
  set.
- M3 remains optional and isolated from default import until its complete
  lifecycle and packaging contract passes.
- M4 optimizations require before-and-after benchmark evidence and can be
  reverted without altering the accepted value contract.
- Generated workbooks and benchmark outputs stay in ignored or CI artifact
  locations unless deliberately promoted as compact durable evidence.

## Intended review splits

1. M0 scenarios, manifests, and visual rubric.
2. M1 dtype policy and preflight validation.
3. M1 native conversion and format-precedence corrections.
4. M2 default profile and examples.
5. M2 aggregated column-rule contract.
6. Each admitted report-composition candidate as a separate slice.
7. M3 optional dependency, lifecycle, and ZIP64 round trip.
8. M4 benchmark baseline before any performance patch.
9. Each measured performance improvement independently.
