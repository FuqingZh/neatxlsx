# XLSX Writer Benchmark Protocol

Version: v1.2
Date: 2026-08-31
Status: current measurement procedure; 2026-09-01 comparison recorded

## Question and prerequisites

Use the repository scripts to measure end-to-end report writing or distinguish
LazyFrame collection, Arrow transport, and XLSX generation costs. This rewrites
the [axiomkit benchmark guide](../archive/axiomkit-xlsx/benchmarks/xlsx_writer/README.md)
for the current API and scripts. Historical results are preserved in the
[source archive](../archive/axiomkit-xlsx/README.md), not adopted as neatxlsx
performance claims.

Use the project Python 3.13 environment and a release native extension:

```bash
pdm sync -G dev
pdm run develop --release
PYTHONPATH="$PWD/python" pdm run python -c 'from importlib.metadata import version; import neatxlsx, neatxlsx._native as n; print(neatxlsx.__file__); print(n.__file__); print(n.__build_profile__); print(version("neatxlsx"))'
```

Verify both printed paths belong to the intended checkout, the profile is
`release`, and installed distribution metadata matches that checkout's package
version. An editable install can otherwise resolve another worktree. Setting
`PYTHONPATH` selects source imports but does not repair stale distribution
metadata; rebuild/install the intended package in an appropriate isolated
environment when the two disagree.
Development setup/build commands mutate the local environment; they are not
needed merely to inspect historical records. The benchmark script rejects a
non-release backend. The pipeline profiler does not enforce the profile itself.

## Single-revision end-to-end benchmark

Run from the repository root:

```bash
pdm run python scripts/benchmark_xlsx_writer.py --profile default --repeat 3 --warmup 1 --out-dir dist/benchmarks/default
pdm run python scripts/benchmark_xlsx_writer.py --profile huge --repeat 2 --warmup 1 --out-dir dist/benchmarks/huge
```

This command characterizes one revision. It is not the acceptance procedure
for comparing two revisions because its samples are not interleaved. The
current script supports only `--backend rust`; archived `--backend both`
commands are historical. Explicit output directories above keep fresh results
separate from imported evidence. Without `--out-dir`, the script writes under
`benchmarks/xlsx_writer/results/`. Neither location is itself a reviewed
baseline.

| --- | --- | --- | ---: | ---: | --- |
| default | DataFrame | `narrow_tall_dataframe_header` | 40,000 | 12 | header |
| default | DataFrame | `wide_medium_dataframe_all` | 10,000 | 37 | all |
| default | Parquet LazyFrame | `narrow_tall_parquet_lazyframe_none` | 40,000 | 12 | none |
| default | Parquet LazyFrame | `narrow_tall_parquet_lazyframe_header` | 40,000 | 12 | header |
| default | Parquet LazyFrame | `wide_medium_parquet_lazyframe_body` | 10,000 | 37 | body |

| huge | Parquet LazyFrame | `huge_tall_parquet_lazyframe_none` | 250,000 | 15 | none |

| huge | Parquet LazyFrame | `huge_wide_parquet_lazyframe_all` | 50,000 | 61 | all |

Column totals include `row_id`. Every input is deterministic. DataFrame
construction and deterministic Parquet-fixture generation happen before timing.
For each Parquet LazyFrame write, the timer includes a new
`scan_parquet -> filter -> expression -> projection -> XLSX` pipeline, so each
warmup and repeat evaluates one fresh LazyFrame source through the public API.
The fixture is never regenerated inside that timer. The script records input
kind and per-scenario `chunk_size` (8,192 rows by default; `--chunk-size` can
override it consistently for a run). There is no random sampling seed.

The script constructs `Autofit(mode=...)` with the default `max_rows=20_000`.
Consequently the 50,000-row `body` and `all` cases sample the first 20,000
logical body rows for widths; they still read every input batch to write all
rows. Pass this same policy to every compared revision. The benchmark records
only timings and output dimensions; the reference and split tests remain the
oracles for cell values, styles, widths, reports, and physical-sheet mappings.

The timer includes workbook creation, writing, save/compression, and context
exit. It excludes fixture construction and the subsequent output validator.
Every warmup and measured workbook is checked for first-sheet dimensions and
row-tag counts, then deleted. JSON and Markdown summaries retain individual
times, aggregate statistics, average output size, environment/package details,
and the backend binary path. This validator is not a cell-value, format,
multi-part, or reader-compatibility oracle; use the
[test plan](../testing/20260728-v1.0-neatxlsx-test-plan.md) for those obligations.

## Pipeline profile and memory

Start with a bounded probe, using a fresh process for each mode:

```bash
pdm run python scripts/profile_xlsx_pipeline.py --mode collect-only --rows 100 --cols 20 --sheets 1 --chunk-size 32
pdm run python scripts/profile_xlsx_pipeline.py --mode arrow-drain --rows 100 --cols 20 --sheets 1 --chunk-size 32
pdm run python scripts/profile_xlsx_pipeline.py --mode xlsx-write --rows 100 --cols 20 --sheets 1 --chunk-size 32 --autofit header --out-dir dist/profile-header
pdm run python scripts/profile_xlsx_pipeline.py --mode xlsx-write --rows 100 --cols 20 --sheets 1 --chunk-size 32 --autofit all --out-dir dist/profile-all
```

The script prints one JSON result to stdout. Retain it alongside the generated
workbook and environment information when recording evidence. `xlsx-write`
keeps its output, but overwrites the same shape/mode filename on a repeated run:
use a distinct `--out-dir` for each record. Collection and Arrow-drain modes
consume one logical table irrespective of `--sheets`; XLSX mode writes the
table once per requested sheet. Compare equivalent workloads rather than
subtracting incompatible timings.

The profiler uses POSIX `resource.getrusage(...).ru_maxrss`: the field named
`peak_rss_kb` is KiB on Linux, but the native value is bytes on macOS. It is a
whole-process high-water mark including input setup and, in XLSX mode, the
post-write XML validation. That validator loads sheet XML into memory, so this
metric is not isolated writer memory. `elapsed_s` also includes that validation,
unlike the benchmark timer. The script is not a Windows memory profiler and its
validator assumes no automatic row/column splitting; use the boundary tests
for split outputs.

After the bounded probe, the archived June plan calls for `2,000 x 1,400 x 2`
and `10,000 x 1,400 x 2` smoke workloads. Increase `--rows`, `--cols`, and
`--sheets` deliberately with sufficient scratch space. The profiler has no
`--max-rows` option; a full-body `all/body` experiment beyond 20,000 rows needs
an explicit `Autofit(max_rows=None)` workload rather than relabeling default
results.

## Recording a comparable baseline

Keep baseline and candidate inputs, modes, sampling limits, formats, chunk
sizes, builds, and validation identical. Record:

- source commit and dirty-tree status, Python/Polars versions, lockfile, native
  path/profile, and ideally binary hash;
- OS, CPU, available memory, filesystem/scratch location, disk capacity, and
  competing load;
- exact commands, repetitions/warmups, raw JSON, time dispersion, output sizes,
  and memory measurement scope;
- independent output checks for values, styles, warnings, widths, and physical
  sheet/report mappings when those are affected.

The scripts do not automatically capture all these fields. Do not invent the
missing metadata. No speedup is established by reducing a conceptual pass
count, and the ten imported February result pairs cannot measure a June
streaming change or a future delayed-width implementation. Any new baseline
must identify the actual compared revisions and rerun the relevant output
oracles.

### Interleaved comparison and verdict rule

Do not compare a DataFrame row with a Parquet LazyFrame row: they answer
different questions. DataFrame rows isolate writer and packaging work; Parquet
LazyFrame rows include one fresh source evaluation through the public API.

Use the fixed dual-environment driver for an acceptance comparison. Store the
result outside both compared checkouts:

```bash
pdm run python scripts/compare_xlsx_writer.py \
  --baseline-root /tmp/neatxlsx-baseline \
  --baseline-python /tmp/neatxlsx-baseline/.venv/bin/python \
  --baseline-source-id BASELINE_GIT_SHA \
  --candidate-root "$PWD" \
  --candidate-python "$PWD/.venv/bin/python" \
  --profile huge \
  --blocks 4 \
  --warmup 1 \
  --order-seed 20260901 \
  --analysis-seed 20260902 \
  --cpu-list 0-7 \
  --polars-threads 4 \
  --include-full-scan \
  --include-computed \
  --out-dir /tmp/neatxlsx-interleaved-huge
```

The driver freezes its order and identities before execution. Each scenario
uses four deterministic ABBA/BAAB blocks, giving eight measured samples per
revision. Every sample runs in a fresh child process using the same worker
script but the declared revision's Python environment and source/native root.
The worker rejects a non-release backend or an import escaping that root.

The worker separately records input-plan, workbook-setup, `write_sheet`, and
`close` wall and process CPU time. The primary metric is paired total wall
time. Stage CPU and process-start-to-stage RSS explain the result but do not
replace the primary endpoint. Output validation and ZIP-member hashing occur
after timing.

Pair adjacent baseline/candidate observations within each block and compute a
deterministic 95% bootstrap interval for the median candidate/baseline ratio.
Require at least eight successful samples per revision even when a smaller
`--blocks` value is used for a smoke run. Apply the frozen gates:

- LazyFrame `body/all`: total-wall interval upper bound below `1.00` and median
  improvement of at least 3%;
- LazyFrame `none/header`: interval upper bound below `1.03`; and
- matching uncompressed ZIP-member names, sizes, and hashes after normalizing
  only the generated `docProps/core.xml` `created/modified` UTC values. Raw
  hashes are retained, and no other field is normalized.

An incomplete process set, wide interval, or target that does not cross both
thresholds is `inconclusive`, not acceptance. Do not add samples after seeing a
preferred direction. Start a separately identified run with a predeclared
larger count or use a quieter host.

For a native zlib comparison, pass `--verdict-policy zlib`. That policy requires
at least a 5% paired total-wall improvement with the interval below `1.00`, no
3% write-stage regression, and the same output parity. Prove the active
compressor separately; timings cannot show that a requested Cargo feature was
actually selected at runtime.

The 2026-09-01 ABI v5/v6 runs and frozen calculations are recorded in the
[single-pass comparison](results/20260901-single-pass-autofit/comparison.md).
That record does not meet the implementation plan's performance gate: it shows
neither a consistent `body/all` improvement nor clean controls across both
profiles. It makes no memory or portable performance claim.
