# neatxlsx Streaming and Autofit Architecture

Version: v1.0
Date: 2026-09-01
Status: current implementation description; canonical one-stream writer path

## Scope and authority

This document expands the [architecture](20260728-v1.0-neatxlsx-architecture.md)
with execution paths, width semantics, and the reason the inherited streaming
plan matters. It describes the current working-tree implementation, with
`rust_xlsxwriter 0.90.2` pinned in [Cargo.lock](../../Cargo.lock). The
[public API contract](20260728-v1.0-neatxlsx-public-api-contract.md) remains the
caller-facing authority. This record describes implementation behavior; it
does not establish package publication or a performance result.

## Current data paths

Python owns caller policy and LazyFrame batching, the PyO3 bridge transports one
Arrow batch stream, and Rust core owns conversion, rendering, delayed width
finalization, and worksheet splitting. Public `Workbook.write_sheet()`
normalizes both DataFrame and LazyFrame input onto the same canonical native
`write_sheet_batches(batches, ...)` v6 bridge method. The native direct
DataFrame, IPC, and dual-stream writer paths have been removed.

| Public autofit mode | Input traversal and writing | Width application |
| --- | --- | --- |
| `none` | One batch stream; each cell is normalized and written once | No automatic width assignment |
| `header` | One batch stream; headers and cells are written as batches arrive | Header widths are applied after stream exhaustion |
| `body` | One batch stream; each body cell contributes while its absolute logical row is within the sampling window | Sampled body widths are applied after stream exhaustion |
| `all` | One batch stream; header and sampled body maxima are tracked together | The larger logical-column width is applied after stream exhaustion |

There is no production two-pass fallback and no transparent retry that
re-evaluates the input. This makes one-shot and nondeterministic inputs safe
from a second evaluation, while ordinary per-batch schema and write errors can
now occur after earlier worksheet rows have been staged.

## Width policy

- `none`: no automatic width assignment.
- `header`: estimate widths from header cells.
- `body`: estimate widths from the selected body rows.
- `all`: take the larger of header and body estimates. It does not mean “all
  rows”.

The public defaults are `max_rows=20_000`, `min_width=8`, `max_width=60`, and
`padding=2`. `max_rows=None` removes the body-row sampling limit. Final width
uses the estimated maximum plus padding, bounded by configured limits and
Excel's 255-unit maximum. Preserve these settings when changing execution;
full-body sampling is a separate performance and behavior choice.

The tracker samples the first `max_rows` body rows of the logical table using
absolute `(row, column)` coordinates. Its widths are retained by logical
column, then projected onto every row page and rebased onto each column part.
Consequently, a widest sampled value encountered on a later row page still
sets the final width of earlier pages. `max_rows=None` keeps tracking body
rows until exhaustion; it does not buffer previous rows.

Width is an estimate, not an Excel rendering oracle. Header, string, boolean,
and retained missing-value text use `rust_xlsxwriter::cell_autofit_width()`.
For sampled numeric cells, the runtime selects the same normal or scientific
final `CellFormatPatch` as the writer, formats it through a per-write cached
`ssfmt::NumberFormat`, then measures that display text with the same upstream
helper. The cache records both parsed and unsupported format strings and is not
created for `none` or `header`; `max_rows` is checked before formatting a body
cell. Parse failures and per-value formatting failures retain the previous
deterministic estimate without failing the workbook.

The tracker retains pixels, converts public character-unit `padding`,
`min_width`, and `max_width` into the Calibri 11 pixel domain, and calls
`set_column_autofit_width()`. Generated autofit columns therefore carry Excel
`bestFit=1`; Excel may enlarge an edited numeric cell later. The initial width
still obeys the configured bounds. The estimate does not measure arbitrary
font metrics or custom font sizes. Upstream gives all non-ASCII characters a
generic width. A narrow measured East Asian safety floor adds four pixels per
eligible scalar in U+3000–303F, U+3040–30FF, U+4E00–9FFF, U+AC00–D7AF, and
U+FF01–FF60; it is based on LibreOffice 6.4 bounding-box evidence on Linux.
It raises the upstream eight-pixel non-ASCII estimate to a twelve-pixel floor
for those scalars, before the configured pixel padding and bounds apply. This
is not a complete CJK implementation: emoji, accented Latin, CJK extensions,
and compatibility ideographs retain the upstream metric. Windows Excel remains
an explicit calibration canary rather than an assumed match.

## Constant-memory mechanics

In the pinned dependency, advancing to a new row flushes prior cell data to a
worksheet temporary file. Already flushed rows cannot be edited. Column widths
are separate metadata: `set_column_width_internal()` updates `changed_cols`
through `store_column_width()` without rewriting row cells.

At save time, `Packager::write_worksheet_file()` emits:

```text
worksheet metadata, including <cols>, then <sheetData>
    -> rows read from the worksheet temporary file
    -> closing sheetData and trailing worksheet metadata
```

The canonical writer uses this sequence:

```text
read each input batch once
    -> convert/write cells and accumulate per-column width maxima
    -> after input ends, apply final widths to all relevant worksheets
    -> save/package the workbook
```

This is online width accumulation followed by explicit width assignment, not
a request to reconstruct flushed cells with a final `Worksheet::autofit()`.
The width accumulator requires `O(logical columns)` additional state. This is
not a total-memory bound: Arrow batches, query execution, formats, worksheets,
and packaging still consume resources. Temporary row-file writes and reads
remain; “single-pass input” does not mean one total filesystem pass or streaming
the finished XLSX directly to a network client.

Dependency source anchors for rechecking after an upgrade:

- `rust_xlsxwriter-0.90.2/src/worksheet.rs`:
  `set_column_width_internal`, `store_column_width`,
  `assemble_xml_file_start`, `write_cols`;
- `rust_xlsxwriter-0.90.2/src/packager.rs`: `write_worksheet_file`.

These are internal implementation observations from source inspection. They
explain why delayed widths are valid with the pinned dependency; they do not
claim a new package publication or performance result.

## Splitting, empty inputs, and failure boundary

Runtime page creation follows incoming row order because the final row count
is unknown. Each physical sheet is registered by stable logical starts
`(row_start, col_start, col_end)`. After the stream ends, the retained static
split planner supplies canonical column-first, then row order, final names,
intervals, and warnings. The writer applies widths, renames staged worksheets,
and reorders only the appended segment to that canonical order. Temporary
names are internal and do not reserve caller-visible final names.

A zero-row input with a nonempty schema uses the supplied schema fallback and
creates the normal empty physical sheet with its headers and applicable width
policy. A zero-column input continues to fail through the public `WriteError`
and Python abort path; that behavior is distinct from a schema-bearing empty
table.

Validation before the first native worksheet mutation remains recoverable.
Once a logical write has appended a worksheet, a later native error poisons the
writer: further writes and `close()` are rejected, and the Python public path
aborts it. This boundary prevents callers from continuing with a partially
mutated workbook. Transactional target replacement still determines whether
the existing output target survives a failed generation.

## Historical compatibility obligations

The [archived axiomkit plan](../archive/axiomkit-xlsx/docs/migration/xlsx_streaming_single_pass_plan.md)
explicitly limited the June 2026 optimization to `header/none`, while also
introducing direct Arrow extraction and dynamic sheet creation. It retained
`body/all` on the planner. The
[archive provenance](../archive/axiomkit-xlsx/README.md#historical-execution-decisions)
records the commits. It does not establish that delayed widths were evaluated
and rejected, or that the library required two passes. The retained
compatibility obligations are to preserve the logical sampling window across
all pages, column-part rebasing, headers, formats, warnings, freeze panes,
empty schema-bearing inputs, exact Excel boundaries, transactional failure
handling, one input evaluation, and output parity. Measured elapsed time and
peak memory remain matters for the separate
[benchmark protocol](../benchmarks/20260831-v1.0-xlsx-writer-benchmark-protocol.md);
the one-stream implementation alone is not a performance claim.
